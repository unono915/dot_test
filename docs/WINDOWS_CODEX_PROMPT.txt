학교 정보자산 관리 프로그램의 개발을 이 Windows PC에서 이어서 진행해 주세요.

저장소는 https://github.com/unono915/dot_test.git 입니다. 클라우드 개발은 중단되었습니다. 이 저장소는 아직 완성 앱이나 설치 프로그램이 아니라 승인된 설계와 개발 도구의 중간 체크포인트입니다.

먼저 다음 파일을 읽고 현재 원격과 로컬 파일을 확인해 주세요.
1. docs/specs/school-asset-desktop-review.md — 승인된 제품 명세와 AC-01~AC-45
2. docs/plans/school-asset-desktop-implementation-plan.md — 구현 계획과 검증 조건
3. docs/WINDOWS_HANDOFF.md — 현재 상태, 실제 명령, 남은 구현 순서
4. README.md, package.json, package-lock.json, scripts/check-electron-sqlite.cjs, tests/toolchain/sqlite-smoke.cjs, tests/support/electron-probe.cjs

기존 설계에 따라 이어서 구현해 주세요. 요구사항 인터뷰나 전체 계획을 처음부터 다시 만들지 말고, 중요한 모순이나 설계 변경이 필요한 쟁점만 질문해 주세요. 전체 제품의 45개 수용 기준을 유지하고 단순 CRUD나 데모로 축소하지 마세요.

현재 상태:
- 공개 명세/계획, 고정 의존성/lockfile, 합성 SQLite 도구 검사와 최소 Electron 진단만 있습니다. src, 실제 앱, 업무 저장 계층, UI, 제품 시험/빌드/패키징 설정과 설치 파일은 아직 없습니다.
- Linux에서 고정 의존성 406개 설치가 성공했습니다. Node 24.19.0 및 Electron 44.5.1의 내장 Node 24.21.0에서 SQLite 3.53.4 로딩, PRAGMA, 실패 트랜잭션 롤백, Online Backup 검사가 각각 1개 통과했습니다. CJS 3개 문법 검사도 통과했습니다.
- 일반 Linux 데스크톱의 최소 Electron 진단은 한글 렌더러와 SQLite 백업, sandbox/contextIsolation true, nodeIntegration false, 렌더러 process/require undefined를 확인했습니다. 격리 환경의 GUI/headless 실행은 실패했으며 보안을 낮춰 우회하지 않았습니다.
- 이는 제품 GUI/보안 전체나 Windows 검증이 아닙니다. 제품 수용 기준 45개와 모든 실제 Windows 수용 시험은 미실행입니다. 의존성 경고가 있었고 전체 보안 검토가 끝난 것도 아닙니다.

환경부터 실제로 확인해 주세요.
- 목표는 Windows 11 x64입니다. Git과 Node 24.x(engines: >=24.19.0 <25), npm이 필요합니다. 공식 출처는 https://git-scm.com/install/windows , https://nodejs.org/en/download , https://docs.npmjs.com/downloading-and-installing-node-js-and-npm/ 입니다. 기존 설치를 우선 확인하고 추가 설치/다운로드/권한이 필요하면 설명하고 승인받으세요.
- Windows Codex에서 GPT-6-Astra와 Ultra가 실제 제공되면 사용하세요. 설치된 모델/추론 설정과 지원 여부를 확인하고, 불가능하면 사실대로 알려 주세요. 사용하지 않는 모델이나 실행하지 않은 검사를 사용했다고 하지 마세요.
- OMX Ultragoal이 이미 설치되어 있고 해당 버전의 실제 목표 기능이 작동하는지 확인하세요. 가능한 경우 공개 명세와 남은 작업에 근거한 새 Windows 목표로 진행하세요. clone으로 클라우드 목표/실행 상태가 이어진다고 가정하지 마세요. 없거나 동작하지 않으면 일반 단계별 TDD로 진행할지 또는 별도 설치할지 확인하세요. 자동 설치나 목표 기능 흉내 내기, 인증/런타임 상태 복사는 하지 마세요.
- 승인, 인증, 네트워크와 sandbox 경계를 유지하세요. 보안 우회 옵션, 인증서 검증 해제, 묵시적 관리자 실행이나 권한 확대는 사용하지 마세요.

새 로컬 개발 폴더에서 시작하는 명령은 다음과 같습니다. Windows 명령 프롬프트(cmd.exe) 기준이며 한 단계가 실패하면 다음으로 넘어가지 마세요. 이미 작업 폴더가 있다면 먼저 미커밋 변경과 브랜치를 확인하고 보존하세요.

git --version
node --version
npm --version
git clone https://github.com/unono915/dot_test.git
cd dot_test
git remote -v
git status --short --branch
git fetch origin
git log -1 --oneline origin/main
git switch -c work/windows-foundation origin/main
npm ci
npm run check:sqlite:node
npm run check:sqlite:electron

브랜치 이름이 이미 있으면 고유 이름을 쓰세요. npm ci는 기존 node_modules를 교체하므로 그 안에 개인 작업물이 없는지 확인하세요. lockfile을 삭제하거나 버전을 임의로 바꾸어 설치 오류를 숨기지 마세요. Windows 설치 성공 여부는 새로 검증해야 합니다.

현재 npm 스크립트는 위 검사 두 개뿐입니다. 존재하지 않는 npm start, npm test, build/typecheck/lint 명령을 실행 안내하거나 통과했다고 하지 마세요. 실제 구현과 설정이 갖추어졌을 때 필요한 명령을 추가하고 검증하세요.

선택적으로 일반 Windows 데스크톱 터미널에서 ELECTRON_RUN_AS_NODE가 설정되지 않은 상태로 최소 진단을 실행할 수 있습니다.
node node_modules/electron/cli.js tests/support/electron-probe.cjs
이는 숨겨진 최소 창/합성 DB 진단이지 업무 앱이 아닙니다. 종료 코드뿐 아니라 JSON의 PRAGMA·백업/한글 값·보안 설정·process/require 미노출을 확인하세요.

바로 다음 작업은 안전한 실제 Electron 앱 셸과 재현 가능한 TypeScript/Vite/Vitest/Playwright 시험 기반입니다.
1. 부정 출처 IPC, 외부 탐색/새 창/다운로드/권한/네트워크 차단과 단일 인스턴스의 행동 시험을 먼저 만들고 실제 RED를 확인하세요.
2. 로컬 번들 전용 app://bundle 출처, 좁은 preload API, 최소 한국어 창을 구현하세요. sandbox/contextIsolation true, nodeIntegration false를 유지하고 main에서 등록된 webContents, main-frame, 정확한 출처, 요청 스키마를 검증하세요. 원시 SQL/임의 경로/셸/전체 IPC를 노출하지 마세요.
3. 최소 구현 후 GREEN과 회귀 검사, 실제 Windows Electron 네이티브 SQLite 로딩을 확인하세요. 현재 진단의 성공을 제품 구현 완료로 대신하지 마세요.

그다음 전체 작업은 다음 순서로 이어 주세요. 세부 계약과 상한, 수용 기준은 공개 명세/계획을 따릅니다.
1. 업무 SQLite 스키마와 독립 세대 카탈로그, 단일 writer/데이터 루트 잠금, 명령 ID·기대 버전·epoch, 업무/감사/명령 결과/revision 원자성, 취소·응답 유실·재시작.
2. 개별 자산·사람·계층형 장소·기본 조회, 현재 관계 ID와 같은 스냅샷의 버전, 재시작 후 공개 조회로 재발견.
3. 실제망·별칭·IPv4·인터페이스·IP 예약/활성/해제 대기/최종 해제/원자적 이전. 실제 점유 IP가 필요한 자산 업무 시험보다 먼저 구현.
4. 배정·일반 반납·이동·대여/반납·수리·분실/회수·퇴역/폐기·append-only 정정과 상세 이력.
5. 배정과 독립적인 관측 회차, 고정 기준 실사, 종료 세션 보존·현재 장부 비교·미해결 업무.
6. 제한된 XLSX 파싱·열 매핑·안정키 검토·재이관 무변경·stale 검토 거절·선택 묶음 원자 적용·안전한 스냅샷 출력. 50,000행 응답성 기준을 먼저 통과한 후 후속 UI 연결.
7. 불변 첨부, 잠금/진행/취소, DB·첨부·설정 일관 백업, 적대적 복원 검증, 세대 전환·새 epoch·강제 종료 복구·이전 세대 열람/롤백·보호된 정리.
8. 전체 한국어 UI와 공개 API 연동, 관계/세션/세대 재발견, 키보드·IME·배율·오류·취소·반복 저장·응답 유실.
9. 실제 Windows 패키징·네이티브 모듈 포함·일반 사용자 설치/재설치/제거·데이터 보존·오프라인·규모/성능·라이선스/도움말·합성 인계 예제·빈 새 PC 복원까지 통합 검증.

모든 구현은 TDD의 RED → 최소 구현 → GREEN → 회귀 순서로 진행하세요. AC-01~AC-45를 통과/실패/미실행 및 실제 증거와 연결하고, 테스트를 건너뛰거나 미구현 handler를 가짜로 성공시켜 완료하지 마세요. 유효한 합성 fixture를 사용하며 실제 업무 명령으로 통합 흐름을 증명하세요.

데이터 무결성/개인정보/보안 경계:
- main이 DB와 최종 업무 전이를 소유하며 감사·명령 결과 실패도 전체 롤백입니다. 중복 명령, 오래된 버전/세대, 원자성을 우회하지 마세요.
- pending_release는 여전히 점유입니다. 퇴직/전원 꺼짐/실사 미발견/반납으로 IP를 자동 해제하지 마세요. 확인 근거와 최종 확인 없이 해제·이전하지 말고 실제 LAN 무충돌을 보장한다고 하지 마세요.
- 관측과 배정, 운영 상태와 물리 확인, 실사 기준과 현재 장부를 분리하세요. 실사 미발견을 자동 분실/폐기로 만들지 마세요.
- 엑셀 미리보기는 DB를 변경하지 않고, 재이관이나 오래된 검토가 최근 수동 수정을 덮어쓰지 못하게 하세요. 복원은 비활성 세대 검증 뒤 전환하며 새 epoch로 이전 폼/작업/파일 승인을 무효화하세요.
- 단일 관리자 오프라인 범위를 유지하세요. LAN 스캔·자동 수집·서버/다중 사용자·클라우드 동기화·자동 업데이트·원격 분석을 추가하지 마세요. 실제 학교 자료, 학생정보, 비밀번호, 인증정보나 방문 기록을 사용하지 마세요.

Windows 네이티브 실행, 한글 IME 조합 중 Enter, 배율, 일반 계정 설치/재설치/제거, 오프라인 전 업무, 패키지 addon, 강제 종료/복구와 새 PC 복원은 실제 Windows에서 증명하세요. Linux/WSL/크로스 빌드 결과를 Windows 통과로 바꾸지 마세요.

검증된 작은 단위로 같은 https://github.com/unono915/dot_test.git 저장소에 commit/push해 주세요. 클라우드 구현은 중단되었지만 다른 변경 가능성은 있으므로 feature branch를 사용하고 게시 전 git fetch origin으로 원격 head와 차이를 재확인하세요. 전체 staged diff와 비밀정보를 검토하고 사용자의 변경을 보존하며 강제 push하지 마세요. push 후 원격 SHA와 직접 링크를 보고하세요. main 통합 전에도 원격 변경과 검증을 확인하세요.
